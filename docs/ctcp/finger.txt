# CTCP FINGER

## Synopsis

```irc
/ctcp <target> finger
```

## Description

Request more information about the user of another IRC client. That client and its user control the returned information, so it may be incomplete, customized, or inaccurate. Support, automatic responses, and throttling depend on the receiving client's configuration; a reply is not guaranteed. See [`ctcp`](../commands/ctcp.md).

EPIC6 provides its responder in [script/ctcp](../../script/ctcp), loaded by [script/builtins](../../script/builtins). The script constructs this text:

```text
name (user@host) Idle seconds second(s)
```

| Field | Source in the supplied responder |
| --- | --- |
| `name` | Nonempty `IRCFINGER` environment variable, otherwise [`default_realname`](../set/default_realname.md), otherwise `Esteemed EPIC User`. |
| `user` | Nonempty `IRCUSER` environment variable, otherwise the portion before `@` in `$X`. |
| `host` | Portion after `@` in `$X`, the current server's recorded userhost. |
| `seconds` | `$E`, the client's input idle time in whole seconds. |

The handler does not independently discover the host or obtain an idle value from the IRC server. It ignores additional request arguments. CTCP request handling and activation settings can prevent automatic replies. The C sender also retains a reply-throttling branch, but [`no_ctcp_flood`](../disambiguation/set_no_ctcp_flood.md) is not a registered setting. The branch updates its timestamp only when dropping replies, so it does not establish a supported or reliable reply-rate limit. Received replies normally pass through [`on ctcp_reply`](../on/ctcp_reply.md) and display as `CTCP FINGER reply from sender: reply-text` unless scripts customize or suppress them.

## Example

```irc
/ctcp john finger
```
