# map script

## Synopsis

```irc
/load map
/map [<server>]
```

## Description

This script supplies a client-side network topology display using [`links`](../commands/links.md) replies when a server-side MAP facility is unavailable. It defines an alias named `map`, replacing ordinary command dispatch to the built-in [`map`](../commands/map.md) while the alias is installed. It uses the `encode()` and `servernum()` compatibility functions from [`builtins`](builtins.md); the script does not load those dependencies itself.

With no server argument, a nonempty `005 MAP` value from `serverctl()` makes the alias send `MAP` through `quote` and return. In that branch, the server provides the map. Otherwise, the alias requests LINKS from the current server, captures numeric 364 entries until numeric 365, and attempts to build a local map.

An explicit server argument always selects the local path and chooses a center from the returned server names. It does not connect to that server or obtain an independent view from it. The renderer retains the hop counts reported by the querying server, rather than recalculating them relative to the selected center.

The script's output uses `[map]` lines with branch markers, server names, hop counts, and descriptions. If the requested center is absent from the collected list, it reports that the server does not appear to be online. That means absent from the returned data, not independently verified offline.

## Requirements and retained-script limitations

Both paths require a usable IRC connection and server support for the request being sent. Servers can restrict LINKS/MAP access, hide topology information, or reject a request. The script cannot recover information the server withholds. The original page's description of seamless fallback was therefore too broad.

The local path installs suppressing, serial-zero numeric 364 and 365 hooks with broad patterns. It does not preserve earlier handlers for the same event/pattern combinations or isolate requests by server. Concurrent map or LINKS requests can mix data and callbacks. The intended completion path renders the map and deletes its `map.links*` assignments, but the current script has a separator defect: `map.finish_links` places its first two ON-removal commands and following FOR command on separate physical lines without separating semicolons. The PF loader joins those lines into one statement, so they are not three independent commands as written. Do not rely on the documented intended hook cleanup and normalization being performed correctly.

The script also has no timeout recovery for a missing end-of-LINKS reply, uses global working assignments, and assumes conventional topology fields and sensible hop counts. It is a retained implementation to inspect and adapt, not a guarantee of a complete or successful topology query.

## Examples

```irc
/load map
/map
/map irc.example.net
```

Replace the final example name with one actually present in the returned LINKS data. These commands remain subject to the dependencies and implementation limitations above.

## History

The original documentation attributes the earlier `imap` script to daemon and records that it supported arbitrary map centering. It describes Undernet's server-side MAP command as inspired by that earlier script, with fewer centering features. The supplied `map` script was written by wd to emulate server-side MAP where unavailable, and the original page dates its first appearance to EPIC4 1.1.6.
