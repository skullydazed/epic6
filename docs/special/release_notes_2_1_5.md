# EPIC5 2.1.5 release notes

Released **May 29, 2021**, commit ID **1945**, release name **Fecund**. Tag `epic5-2.1.5` and release commit `7903eda5` confirm the identity and date. These are historical EPIC5 notes; current EPIC6 qualifications are identified below. See the [release index](release_notes.md).

## May 25, 2021: Autoconf update

The release replaced the Autoconf 2.13-generated configure script with one generated by Autoconf 2.69 and fixed Python 3.8-or-later build support. That generator version describes the release, not an instruction to regenerate current EPIC6 with Autoconf 2.69. The current supplied configure script identifies a newer generator, and optional Python requirements follow the current `configure.ac` checks.

## May 20, 2021: Window UUIDs

Each new window receives an immutable UUID, accessible through:

```text
$windowctl(GET <window> UUID)
```

The identifier is stored without hyphens, allowing it to be used as part of a variable name. It remains attached to that window rather than changing with a user-visible reference number. It is not a persistent identity for a window recreated in a later client session.

The original called these identifiers globally unique. They are generated UUID4 values, not a registry-backed guarantee against every possible collision. Current source still generates a no-dashes UUID at window creation and exposes it through the getter; it does not provide a UUID setter. See [`windowctl`](../functions/windowctl.md) and [`uuid4`](../functions/uuid4.md).

## May 20, 2021: Claiming channels

The release introduced a script opportunity to choose a channel's window during channel setup. EPIC proposes a window, invokes CHANNEL_CLAIM, and then applies a successful claim or retains its proposal.

This concerns adding or recreating the client's channel record, commonly when the server reports the client's own JOIN. It is not a hook for assigning a new window whenever any other user joins an already-known channel. The original also distinguished deliberate movement of an established channel through `/join` or `/window channel`: claiming is not a mechanism to veto those user-requested moves.

### CHANNEL_CLAIM event

The hook supplies:

| Argument | Meaning |
| --- | --- |
| `$0` | Server reference number. |
| `$1` | Channel being assigned. |
| `$2` | Proposed window identifier. In current source this is an internal window identifier, not necessarily its user-visible refnum. |

During this interval, a handler can nominate a window on the same server using WINDOW CLAIM. The last successful claim wins; without a valid claim, EPIC keeps the proposed window. The hook's suppression result does not cancel channel creation or assignment. See [channel_claim](../on/channel_claim.md).

### WINDOW CLAIM operation

```text
/window <window> claim <channel>
```

Supply the channel from `$1` while its claim hook is running. The selected window must belong to the server from `$0`, and the channel must currently be claimable. A mismatched server or out-of-interval claim fails; the operation does not send a JOIN or independently move an established channel. The original anticipated relaxing the server restriction later, but current EPIC6 still checks it. See [window claim](../window/claim.md).

## May 20, 2021: UUID4 NODASHES

The release added the defined `NODASHES` argument:

```text
$uuid4()
$uuid4(NODASHES)
```

The first returns a hyphenated UUID4 string; the second returns the compact representation. The original illustrated using it within an assign name:

```irc
@ a.$uuid4(NODASHES) = [whatever]
```

The release reserved all other argument forms for future changes. Current source compares the complete argument text with `NODASHES` case-insensitively and otherwise selects the ordinary form, but that fallback does not create a compatibility promise for undocumented arguments. The UUID reference also explains the current random-generation error limitation.
